2. CÓMO UI Y PPTX COMPARTEN AHORA LA PREPARACIÓN

  Ambos consumen prepareCostoUsoResult(input) con exactamente el
  mismo motor. La función acepta ahora DOS modos mutuamente
  exclusivos:

    requestedRange: { from, to }
      Uso: PPTX. El helper filtra weeks por [from, to] cronológico y
      genera etiquetas requestedRange / effectiveRange /
      externalAnchorWeek.

    weekList: any[]
      Uso: /dashboard/costo-uso. La UI aplica sus filtros locales
      (semana única / last4 / last8 / month / custom) y pasa el
      subset resultante. El helper NO reintenta filtrar.

  Se lanza excepción si se pasan ambos o ninguno; no hay caminos
  silenciosos ni defaults tácitos.

  Confirmaciones documentales (por lectura del código, no por
  ejecución):
    - Mismo restaurante:  cada select de data-fetcher se filtra por
                          restaurant_id.
    - Mappings:            costoUsoContext.mappings.
    - Ajustes:            costoUsoContext.adjustments.
    - Descuentos:         costoUsoContext.opDiscountMappings, ligado
                          al modo net/gross vía includeOpDiscounts.
    - Presencia teórica:  buildWeekData / buildPeriodData /
                          aggregateSeries respetan
                          Object.prototype.hasOwnProperty y el flag
                          hasProductMix (misma lógica para UI y PPTX).
    - Diagnósticos:       rangeDiagnostics se produce con el mismo
                          diagnoseRange en ambos consumidores.
    - Consolidación:      la absorción del anchor externo y las
                          intermedias es la misma (misma serie).

3. CONTEXTO ANTERIOR AL FILTRO

  data-fetcher.ts ahora descarga TODAS las semanas del restaurante
  (hasta 52, mismo criterio que la página productiva) en el campo
  costoUsoContext.engineWeeks. Este universo permite que
  buildPeriodSeries encuentre:
    - Anchor externo (semana previa al primer week seleccionado).
    - Semanas intermedias sin inventario dentro del período efectivo.

  Las ventas y compras de semanas FUERA del período efectivo NO se
  incluyen en el cálculo — el motor las excluye del cierre. Se agrega
  aislamiento con RLS por restaurant_id.

  Selección no consecutiva:
    config.weeks se guarda tal cual en costoUsoContext.requestedWeeks.
    Nueva utilidad areConsecutiveWeeks() en generate-pptx detecta
    saltos (por ejemplo, W10 + W15). Cuando no son consecutivas, la
    diapositiva:
      - NO reduce la selección a un rango [min..max].
      - Muestra advertencia con las semanas exactas seleccionadas.
      - Indica que el período efectivo lo determinó el motor y no
        el intervalo continuo entre extremos.

4. OPCIONES DE VENTAS Y ETIQUETAS

  Nuevo tipo CostoUsoSalesBase = 'net' | 'gross'.
  ExportConfig.costoUsoSalesBase se conecta a includeOpDiscounts.

  Etiquetas visibles en el Export Center:
    Ventas netas  — "Equivale al toggle '+Desc. Op.' OFF de la UI."
    Ventas brutas — "Incluye la diferencia completa net→gross. NO
                     aísla descuentos operativos."

  La diapositiva agrega SIEMPRE una advertencia con la base de
  ventas usada y el equivalente en la UI, para poder comparar
  resultados con el mismo contexto sin ambigüedad. La corrección
  comercial "solo descuentos operativos" sigue pendiente; ninguna
  opción de la exportación pretende que ya se aísla.

  Correspondencia UI ↔ PPTX:
    UI toggle "+Desc. Op." OFF  ↔  PPTX 'net'
    UI toggle "+Desc. Op." ON   ↔  PPTX 'gross'

5. DÍAS DE OPERACIÓN AUSENTES

  Cambios en el motor:
    EngineContext.operatingDays acepta number | null.
    buildWeekData / buildPeriodData / aggregateSeries devuelven
    dias_inv = null cuando operatingDays es null. Ninguna otra
    métrica se ve afectada — uso, teórico, %s, variación, ventas y
    diagnósticos siguen calculando igual.

  Cambios en data-fetcher.ts:
    operatingDays pasa `restRes.data?.operating_days ?? null` sin
    fallback silencioso.

  Cambios en generate-pptx.ts:
    Sin fallback a 6. Cuando operatingDays es null la diapositiva
    emite:
      "operating_days no definido: días de inventario queda como no
       calculable en esta exportación."
    El resto del reporte se publica normal — ninguna otra métrica
    se bloquea por esta configuración ausente. No se cambia la
    configuración del restaurante.

  La UI mantiene su carga previa (`restRes.data?.operating_days || 6`),
  para no cambiar sin aviso el comportamiento visible del dashboard;
  ese es un pendiente separado que se puede coordinar cuando toque.
