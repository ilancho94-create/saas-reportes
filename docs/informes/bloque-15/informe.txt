2. CÓMO UI Y PPTX OBTIENEN CONTEXTO EQUIVALENTE

  Nuevo módulo compartido:
    src/lib/costo-uso/supabase-context-provider.ts
    → createSupabaseContextProvider(supabase, restaurantId, weekIds)
      Devuelve un ContextQueryProvider — MISMA interfaz que consume
      loadCostoUsoContext. No duplica la lógica de paginación; solo
      traduce del cliente Supabase a las dos operaciones que el
      loader necesita. Aislamiento por restaurante en ambas queries
      (.eq('restaurant_id', restaurantId)).

  Camino en el PPTX (fetcher):
    fetchExportData → loadCostoUsoContext(providerSupabase) →
    ExportData.costoUsoContext.engineWeeks + contextStatus.

  Camino en la UI (page.tsx):
    loadData carga las últimas 52 semanas del restaurante para
    poblar el listado de semanas seleccionables.
    Cuando `filtered` cambia (por cualquier filtro), un useEffect
    dispara loadCostoUsoContext con el mismo adapter Supabase para
    la selección actual, con un contador `contextLoadId`:
      - Cada request incrementa el contador.
      - Solo la respuesta cuyo id === contador vigente sobrescribe
        estado.
      - Cualquier respuesta anterior (tardía) se descarta sin pisar
        la selección actual.
    Los resultados se combinan con los 52 iniciales en
    `contextualWeeks` (dedup por report.id, orden asc); ese universo
    es el que va a prepareCostoUsoResult.

  Se distingue claramente:
    - Listado de semanas seleccionables → weeks (52 más recientes).
    - Datos completos para calcular la selección → contextWeeks
      (semanas seleccionadas + ventana previa iterativa).
    - Contexto anterior de inventario y semanas intermedias → parte
      de contextWeeks; loadCostoUsoContext las trae con paginación
      hasta encontrar el anchor real o alcanzar el límite absoluto.

  Se preservan:
    - Aislamiento por restaurante (RLS y filtros .eq inalterados).
    - No hay descarga silenciosa de "todo el historial".
    - Selecciones históricas antiguas ya no quedan limitadas al
      cache de 52; el loader iterativo aporta el anchor real.

3. no_prior CON INVENTARIO INICIAL PRESENTE / CERO / AUSENTE

  El motor ahora comprueba explícitamente por categoría cuando NO
  hay anchor previo:

    invPreviousPresent =
      expected accounts for this category in ACCOUNT_MAP.length > 0
      && closing.inventory.by_account has an account of that
         category with previous_value !== undefined && !== null

  Cero explícito califica como presente. Ausencia (campo faltante o
  cuenta ausente) no. Un cliente que responde con by_account = []
  jamás produce invPrevious silencioso.

  Nuevo VarianceReason: 'no_initial_inventory'
    Ruta de decisión (reasonForCategory):
      catSales < 0             → negative_sales
      catSales === 0           → zero_sales
      !invPreviousPresent      → no_initial_inventory
      theoPresent              → ok
      else                     → partial_theo | no_theo_source

  Cuando invPreviousPresent === false:
    - variacion = null (no se reconstruye desde uso − theo).
    - dias_inv = null (denominador desconocido).
    - uso sigue calculándose con clampeo Math.max(...,0) — política
      de negativo sin cambios.
    - _inv_previous_present se expone en el output para que UI y
      PPTX puedan mostrarlo.

  ui-helpers.ts:
    VARIANCE_REASON_LABEL['no_initial_inventory'] =
      "no calculable · sin inventario inicial de referencia en la
       categoría"
    VARIANCE_REASON_LONG['no_initial_inventory'] =
      "No hay conteo de inventario anterior para esta categoría y
       el reporte actual no trae el campo previous_value. Sin
       límite inicial, la variación no es calculable."
